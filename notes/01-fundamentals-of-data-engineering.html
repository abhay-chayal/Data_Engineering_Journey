1 What is data engineering? ▶ 4:11

There are thousands of definitions online. The instructor’s working definition:

DefinitionTake raw, messy data with no relationships between sources → transform it → serve it to stakeholders as clean, structured data models.
Raw datamessy, unrelated
→
Transformclean, link, shape
→
Serveto stakeholders

The chef analogy

A data engineer is a chef: raw vegetables (raw data) come in, the chef cooks them (transformation), and serves a proper dish (data models) that stakeholders can actually “digest”. Handing someone raw potatoes and salt is technically food, but not usable.

Why do we need data engineers?

  • Data volume has exploded, and businesses want data-driven decisions.
  • Someone must move data from one place to another and transform it on the way, so quality is high.
  • That demand is why job postings and pay are high.
Study tip from the videoUnderstand the concept, don’t memorise a definition. Draw small, silly diagrams and analogies in your notes — they’re faster to revise than theory.

Interview“What are the three pillars of data engineering?” → Generation, Transformation, Serving.

Pillar 1 — Data generation ▶ 14:30

  • Any activity creates data: placing an Amazon order (click, quantity, address, payment, confirmation), searching a movie on Prime, a phone call in your bill, a Google search.
  • Sources can be CSV files, databases, or APIs (a connector between applications/websites used to pull information).
  • Generated data is saved to storage. The data engineer consumes from that storage; like a chef, you don’t care who bought the carrots, only that they’re there.

SQL databases

Relational, structured data (tables, rows, columns).

NoSQL

Means “not only SQL” — for unstructured / semi-structured data that doesn’t fit neat tables.

Pillar 2 — Data transformation ▶ 20:53

  • The data engineer’s “favourite spot”: you typically spend 70–80% of your time here.
  • Source systems are usually managed by a DBA (database administrator) — not you. You take their messy, possibly unlinked data and build a clean database.
  • The output is curated data — efficient for reporting and for downstream users.

Pillar 3 — Data serving ▶ 24:40

  • Cooked food sits in a big container; you can’t tell customers “eat from that”. You serve small portions for different customer needs.
  • In data terms: instead of the big dump, you create data models for each type of consumer.
Recap
  • Generate → Transform → Serve. Chef analogy throughout.
  • Transformation is where most time goes; output is curated data.

3 Upstream & downstream ▶ 29:09

Think of a stream of water: whatever is before you in the flow is upstream; what comes after is downstream. It describes data flow, not seniority.

UpstreamDBAs, software / web developers who own the sources
→
You — data engineer
→
Downstreamdata analysts, data scientists, analytics managers
  • In small companies, developers may manage the data source themselves.
  • You get requirements from downstream, data from upstream, and must sync both.
  • Talk regularly to both sides — sometimes you need upstream to change the source for a project. Keep both relationships healthy.

4 OLTP vs OLAP ▶ 35:23

OLTPOnline Transactional Processing
OLAPOnline Analytical Processing
OLTP databaseOLAP database (= data warehouse)
PurposeStore transactional data (e.g. banking transactions, user clicks) as it happensAnalysis & reporting over large volumes
Optimised forWrites & updates (small chunks, often)Reads (heavy queries on lots of data)
ModelingRelational modeling — normalization (1NF, 2NF, 3NF)Dimensional modeling (facts + dimensions)
Owned byDBA (it’s your source)Data engineer — you own it
ExamplesPostgreSQL, MySQL, MS SQL Server, OracleSnowflake, Azure Synapse, Redshift, BigQuery

Why do we need OLAP at all?

The OLTP database grows huge — every second, every millisecond. Pointing reports straight at it would make them “die”. So we build a separate OLAP database tuned for reads, and reports query that instead.

Normalization notes

  • Normal forms exist up to ~6, but practice stops at 3NF — beyond that is hard to manage.
  • As a data engineer you only need basics: normalization concepts and how to join tables. Focus your energy on the OLAP side.
InterviewOLTP vs OLAP: write-optimised, normalised, source system vs read-optimised, dimensional, analytics system.

5 ETL — Extract, Transform, Load ▶ 51:22

ETL is the process that builds the OLAP database / data warehouse from the OLTP source.

Data warehouseOLAP

Why pipelines?

Doing it once isn’t enough — the source keeps updating (say, every hour). We don’t repeat the work by hand; we build an ETL / data pipeline that extracts, transforms and loads automatically.

AnalogyA water pipeline: the tank is the source, and you just open the tap — you don’t carry buckets each time.

6 Data warehouse & layers ▶ 55:22

Data doesn’t go straight from source into the warehouse. It passes through two layers (think of them as folders):

Source
→ extract →
Staging layer
→ transform →
Core layerfacts & dimensions
  • Staging layer — where extracted data lands first.
  • Core layer — the dimensional data model (facts + dimensions).
InterviewWhy stage at all? You shouldn’t query/transform directly against the source — it can slow the source down. Land a copy in staging, then work from there.

Two kinds of staging

Transient

Temporary. Today’s data lands, gets used for the core layer, and is truncated (deleted) before the next load so already-used data isn’t reused.

Used ~99% of the time.

Persistent

Keeps the history of what was staged over time.

Rare; depends on the project.

7 Incremental loading ▶ 1:01:54

A data-fetching strategy: after the first full load, only bring in what’s new.

Example from the video
Source has Jan 2023 → 01 Jan 2024
→
First load: everything
Next day source adds 02 Jan 2024
→
Load only 02 Jan → staging → core
  • Why re-pull everything when you already have it? It wastes computation.
  • The cycle repeats each run: new data → staging → core.
  • This is the standard practice in data engineering — you don’t pull all the data again and again.
Interview“What is incremental loading and how would you apply it?” is a favourite question.

8 Dimensional data modeling ▶ 1:06:33

The modeling technique for OLAP: store data as one fact table linked to several dimension tables. (OLTP uses normal forms; OLAP uses this.)

Fact table

Only numeric values — price, bill, MRP, quantity, weight — plus the keys/IDs that link to dimensions.

Dimension tables

Everything else — descriptive, contextual, categorised data. Group related attributes:

  • customer_dim: name, address, card info
  • product_dim: product name, category

Because dimensions cluster attributes by business meaning, the data is denormalised (semi-/less-normalised) — all customer info lives in the customer table, all product info in the product table.

Star schema vs snowflake schema ▶ 1:11:45

★ Star schema

customer_dim
product_dim
FACT
date_dim
store_dim

The fact is the centre; each dimension attaches directly — looks like a star. ~99% of real-world use: fast to query, easy to manage.

❄ Snowflake schema

→
product_dim
→
FACT

Dimensions form a hierarchy (one dimension refers to another, which refers to the fact). Branches like a snowflake. Harder to manage, so rarely used — but know it.

InterviewFacts hold numeric measures; dimensions hold descriptive context. Star = dimensions directly on the fact; snowflake = hierarchy of dimensions.

9 Slowly changing dimensions (SCD) ▶ 1:15:35

One of the top-3 most important topics (per the video)Dimensions hold descriptive data, and that data changes. SCD types are the strategies for handling those changes. Types 0, 1, 2 and 3 are the ones used in practice.

The scenario used throughout

A product dimension. In the source, product 3 (com) was in clothing, but its category changes to hair accessories. How should the dimension reflect it?

Before the change
product_idnamecategory
1honeyfood
2shirtclothing
3comclothing

Type 0 — no change

The dimension is assumed fixed, so there’s nothing to keep updated. Hence “type 0” — it isn’t really a handling strategy.

Type 1 — overwrite (“upsert”) ▶ 1:15

UPSERT = UPDATE + INSERT. The new value simply overwrites the old; history is lost.

After (type 1)
product_idnamecategory
1honeyfood
2shirtclothing
3comhair accessories
4shoesfootwear (new row)
  • For each incoming record: ID not found → insert; ID found → update.
  • Records with unchanged values are technically “updated” too, but you see no difference.
  • The most used SCD (~70–80% of the time): easy to manage and performant, since no history is kept.
InterviewIf asked to “apply upsert”, they mean SCD Type 1.

Type 2 — keep full history ▶ 1:25:22

Add three columns to the dimension: start_date, expiry_date, and an in_use flag. Instead of overwriting, insert a new row and close off the old one.

After (type 2) — change effective 2 Jan 2024
product_idnamecategorystart_dateexpiry_datein_use
1honeyfood01-Jan-202401-Jan-3000yes
2shirtclothing01-Jan-202401-Jan-3000yes
3comclothing01-Jan-202402-Jan-2024no
3comhair accessories02-Jan-202401-Jan-3000yes
  • A far-future expiry date (e.g. year 3000) means “still current”.
  • Rarer than type 1, but you must know it: “keep the history” → Type 2.

Type 3 — keep the previous value ▶ 1:28:33

Add a previous_category column. Preserves the prior value without managing date columns. No timeline, just “current” and “previous”.

Extra (not from the video): SQL sketch of Type 1 and Type 2 
-- Type 1: upsert (overwrite)
MERGE INTO dim_product t
USING stg_product s ON t.product_id = s.product_id
WHEN MATCHED THEN UPDATE SET t.name = s.name, t.category = s.category
WHEN NOT MATCHED THEN INSERT (product_id, name, category)
                      VALUES (s.product_id, s.name, s.category);

-- Type 2: close the old row, then insert the new one
UPDATE dim_product SET expiry_date = '2024-01-02', in_use = 0
WHERE product_id = 3 AND in_use = 1;

INSERT INTO dim_product (product_id, name, category, start_date, expiry_date, in_use)
VALUES (3, 'com', 'hair accessories', '2024-01-02', '3000-01-01', 1);

10 Data lake ▶ 1:30:13

Data warehouses only handled structured data (tables, rows, columns). As data grew exponentially, that stopped being practical. A data lake stores structured, semi-structured (CSV, JSON) and unstructured data.

Data lake vs data warehouse ▶ 1:33:10

Data warehouseData lake
Data typesStructured onlyStructured, semi-structured, unstructured
SchemaSchema-on-write — defined before data is stored (like DDL before inserting)Schema-on-read — store raw first, define schema after
Storage costHigherVery cheap (the business reason it won)
Performance—Cost & query performance better, per the Microsoft comparison shown
Don’t throw your warehouse notes awayThe lake doesn’t make warehouse knowledge useless — the next section shows it all gets reused.

12 Row-based vs column-based file formats ▶ 1:41:46

The difference is how data is laid out on disk. Using this table:

idnamecategory
1honeyfood
2shirtclothing
3comclothing

Row-based

Examples: CSV, Avro

1 honey food | 2 shirt clothing | 3 com clothing

Whole records written one after another → great for writes and updates. Used on the OLTP side.

Column-based

Examples: Parquet, ORC

1 2 3 | honey shirt com | food clothing clothing

SELECT id FROM … reads one contiguous column; a row format must hop through every record. Great for fast reads — OLAP and big data.

13 Delta Lake ▶ 1:49:17

In one lineDelta is an open table format built on top of Parquet that adds a transaction log.

Plain Parquet stores each file’s metadata (column definitions, schema) inside the individual file. Delta keeps the information in a central transaction log — a folder of JSON files recording every operation (version 1 update, version 2 delete, rollback…). That enables:

⏱ Time travel / versioning

Update → V1, delete → V2. Deleted by mistake? Go back to V1.

🧬 Schema evolution

Source suddenly has a 6th column? Delta can accept it.

🔒 ACID transactions

Atomicity, Consistency, Isolation, Durability — what PostgreSQL/MySQL give you, now on lake storage.

You get warehouse-like behaviour at low cost, because the data is still just Parquet files plus the log.

14 Big data & its frameworks ▶ 2:01:50

Big data is simply very large data. The instructor notes that data is now so large the “big” prefix is barely needed. To work with it you use big data frameworks:

Apache Kafka

Streaming / real-time data at large volume.

Apache Airflow

Orchestration — managing the order and scheduling of many pipelines (like orchestrating music).

Apache Hive

SQL-like — create external tables/databases over big data.

Apache Spark ⭐

The centre of big data processing; most in demand.

Databricks

Management layer for Spark; manages its clusters.

15 Distributed computing & Spark architecture ▶ 2:05:46

Distributed computing: instead of one machine doing the work, combine many (think 20 lab computers acting as one big computer). Many machines together form a cluster.

You submit a job
↓
Driver nodethe brain — orchestrates, assigns work, does no processing
↓ ↓ ↓
Worker nodeexecutes
Worker nodeexecutes
Worker nodeexecutes
↑ results back to you
  • A node = a machine/computer.
  • Exactly one driver node per cluster; the rest are worker nodes that run the transformations/code.
  • Analogy: split an assignment among 10–20 friends — the group finishes far faster.
  • Databricks removes the burden of managing clusters: you just configure how much compute you need.

What is cloud computing? ▶ 2:14:28

Owning 100 computers (CPU, RAM, storage each) is expensive, and your needs fluctuate (e.g. 150–200 during a festive season). A cloud provider owns thousands of machines and rents them to you:

  • Pay only for what you use (use 80 → pay for 80).
  • Scale up in minutes instead of rushing to buy hardware.
  • You don’t own or maintain the hardware; the provider handles security.
  • Accessed over the internet.
Learn one cloud, not allServices are the same across clouds; they’re just renamed. The instructor recommends starting with Azure: strong demand/growth, and a free account with $200 credit for the first 30 days.

17 Medallion architecture ▶ 2:20:20

A data architecture used in cloud data engineering — similar in spirit to the staging idea. Data (batch or streaming) moves through three layers, getting cleaner at each step:

🥉 Bronze

Raw / landing zone. Data as-is from the source.

Rule #1: no changes — no transformation, no schema needed.

🥈 Silver

Cleaned & transformed. Define structure, enforce schema, evolve schema if needed.

🥇 Gold

Ready to serve. Facts & dimensions or aggregated tables, per downstream requirements.

InterviewHot topic: bronze = raw, no change · silver = cleaned/transformed · gold = modeled and served.

18 Azure services, one by one ▶ 2:31:18

Azure Event Hubs 2:31

Stores streaming (continuous) data for real-time analytics. The answer to “which Azure service stores streams?”

Azure SQL DB 2:32

Cloud version of SQL databases like MySQL/PostgreSQL. Same SQL commands (SELECT, UPDATE, DELETE, DDL, TCL, DCL). Used to create OLTP databases.

Azure Data Lake Storage Gen2 2:35

Stores all data types. Lives inside a storage account.

Azure Data Factory 2:39

The Azure ETL tool: move data, orchestrate tasks, many connectors. Low-code, not no-code.

Azure Databricks 2:41

Transforms big data with Spark clusters, managed for you (you only configure compute).

Azure Synapse Analytics 2:43

Cloud data warehouse — equals Snowflake / Redshift / BigQuery. Build facts and dimensions here.

Power BI 2:45

Reporting. Connects to the gold layer’s star schema to build KPI dashboards (pie/line charts), viewable on phone or laptop.

Inside a storage account

  • Data lake (containers) · tables (NoSQL / key-value) · file shares · and one more service the instructor couldn’t recall.
  • Hierarchical namespace: a container is like a folder, and you can nest folders inside it as deep as you like. This is the key difference between a data lake and plain blob storage, and it matters for organising big data.

Self-test (tap to reveal)

Why do we stage data before the core layer?
So you don’t query or transform directly on the source (it slows it down). Land it in staging, then build core from there.
Which SCD do you use if the business wants the history kept?
Type 2: add start date, expiry date and an in-use flag, and insert a new row for each change.
“Apply upsert” — which SCD type is that?
Type 1: update if the record exists, insert if it doesn’t, overwriting the old value.
Why is column-based storage better for OLAP?
A query reads a whole column from contiguous storage in one go; row-based storage has to hop through every record.
What does Delta add on top of Parquet?
A transaction log (JSON files) giving versioning/time travel, schema evolution and ACID transactions.
Explain Spark’s architecture in two lines.
A cluster has one driver node (the brain; assigns tasks) and many worker nodes (execute the transformations). Results flow back to you.
What are the bronze, silver and gold layers?
Bronze: raw, no changes. Silver: cleaned, transformed, schema enforced. Gold: facts/dimensions or aggregates, ready for consumers.
Why use the cloud instead of owning computers?
Pay for what you use, scale in minutes, no hardware to own or maintain, provider handles security.
